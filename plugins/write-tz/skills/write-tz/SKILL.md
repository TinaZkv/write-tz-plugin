# Навык: написание ТЗ

Этот навык — про **как** писать ТЗ. Содержание (терминология продукта, формат
вывода, матрица ролей, фирменные ограничения) берётся из контекста проекта —
файла `CLAUDE.md`, бизнес-документов, тикетов. Навык их не подменяет и не
выдумывает.

## Принцип №1: не достраивать молча

Главный источник плохих ТЗ — правдоподобный вымысел. Если механики,
UI-текста, состояния или правила нет ни в макете, ни в пояснении, ни в
документах проекта — **не сочинять**. Подсветить дыру и уточнить у автора
(см. «Работа с открытыми вопросами»). Явная дыра лучше уверенного вранья:
дыру видно, вранье приходится вылавливать в QA.

## Принцип №2: бизнес-контекст важнее CLAUDE.md при конфликте

Если бизнес-документ проекта и `CLAUDE.md` расходятся по конкретному решению
(термин, скоуп, граница) — прав бизнес-документ как более свежий. **Расхождение
не разрешать молча:** подсветить пользователю и предложить обновить `CLAUDE.md`.
Стоп-слова и термины — самый автоматически применяемый кусок контекста, и
устаревший список тихо испортит весь документ.

## Рабочий цикл (от входов до файла)

1. **Собрать входы** (см. ниже). Не начинать черновик, пока не проверено
   наличие контекста, макетов и матрицы ролей.
2. **Прочитать всё:** бизнес-контекст целиком, каждый макет (картинку — глазами,
   пояснение — если есть), смежные закрытые тикеты.
3. **Блокирующие вопросы — сразу.** Если дыра меняет структуру ТЗ (нет роли,
   неясна основная механика, противоречие источников) — задать вопрос автору
   до черновика, не дописывать на ложном предположении.
4. **Собрать черновик** по структуре ниже. Дыры по ходу — помечать видимым
   маркером прямо в тексте (см. «Маркер незакрытого»), а не заполнять догадкой.
5. **Батч уточняющих вопросов** — собрать накопленные неблокирующие вопросы и
   задать автору одним блоком. Ответы вплести в разделы.
6. **Финализировать:** снять все маркеры (закрыты ответом) либо перенести
   остаток в раздел «Открытые вопросы» с пометкой «ждёт инженера/отложено».
7. **Самопроверка по чек-листу**, проверка валидности разметки.
8. **Записать в файл** (см. «Выход — файл») и отдать автору.

## Перед началом — собрать входы

**Шаг 0 — развернуть/обновить базу знаний продукта.** Перед чтением файлов
убедись, что база знаний есть локально и актуальна.

**Как определить путь к базе:**

Принцип: **сначала найти путь самому из любого доступного источника; явно
спрашивать — только если нигде не нашёл или не уверен.**

1. **Найти путь в доступном контексте (в порядке приоритета):**
   - **(а)** проектный `CLAUDE.md`, раздел «База знаний» с абсолютным путём —
     явный override, высший приоритет;
   - **(б)** любой другой загруженный контекст, где названо расположение базы:
     глобальный `CLAUDE.md`, память / `IDENTITY.md`, ранее настроенный
     `@import` на `product-knowledge-base`.

   Нашёл путь — **использовать его и объявить источник и путь** («база нашлась
   по пути из <источник>: <путь>»), чтобы пользователь мог поймать устаревший
   или чужой. Несколько источников — приоритет у (а).

2. **Спрашивать явно — только если не нашёл или не уверен.** Путь нигде не
   назван; либо кандидатов несколько и неясно, какой брать; либо найденный путь
   на диске не существует (папку перенесли, диск отключён). Тогда НЕ угадывать,
   НЕ сканировать диск, НЕ клонировать молча — задать вопрос и дождаться ответа
   сообщением:

   > Где на этой машине лежит папка базы знаний `product-knowledge-base`?
   > Пришли абсолютный путь (она может быть где угодно, хоть на внешнем диске).
   > Если базы ещё нет — скажи, и я склонирую её (по умолчанию в
   > `~/product-knowledge-base` или в путь, который укажешь).

   - Дал путь → работать с ним (ниже).
   - Базы нет → склонировать (ниже) в указанный им путь либо, с его согласия, в
     дефолт `~/product-knowledge-base` (Windows
     `%USERPROFILE%\product-knowledge-base`; домашнюю папку резолвить в
     рантайме, не хардкодить пользователя и не `/mnt/c/Users/…`).
   - **Предложить записать путь в проектный `CLAUDE.md`** (раздел «База
     знаний», образец — рядом в `CLAUDE.md.ba-example`), чтобы в следующий раз
     не спрашивать.
   - **Headless-прогон (спросить некого):** не блокироваться на вопросе — взять
     дефолт `~/product-knowledge-base` (склонировать/обновить там) и отметить в
     отчёте, что путь не подтверждён пользователем.

**Что делать по определённому пути:**

- **Папка есть** (внутри `.git`) — обновить: `git pull` в этой папке (по
  текущей ветке, без принудительного указания ветки).
- **Папки нет** — склонировать базу туда:
  `git clone git@gitlab.pltrm.net:zykova/product-knowledge-base.git <путь>`.
  Продуктовое знание (`CLAUDE.md` + `docs/reference_*.md`) лежит на ветке по
  умолчанию (`main`) — свежий `clone` попадает на неё сам, отдельный checkout
  не нужен. Ветку насильно не переключать: если пользователь осознанно держит
  базу на другой ветке — уважать его выбор.
- **Путь объявлен в `CLAUDE.md`, но папки по нему нет** (внешний диск отключён,
  папку перенесли) — НЕ клонировать дубль молча: предупредить («объявленный
  путь `<…>` недоступен — диск не подключён?») и уточнить у пользователя,
  прежде чем клонировать.
- **Команду выполнять нативно для окружения пользователя** — обычный `git` в
  PowerShell / Git Bash; только если пользователь сам работает через WSL —
  из WSL. Не зашивать чужого пользователя WSL (`-u …`) или префикс `/mnt/c/…`.
- **Различать причину сбоя clone/pull — лечение разное:**
  - *permission denied / access rights* — не настроен SSH-ключ к
    `gitlab.pltrm.net`; попросить настроить ключ.
  - *connection timed out / could not resolve host* — нет сети или не поднят
    корпоративный VPN (GitLab внутренний); попросить подключить VPN и повторить.
- **Если база уже есть локально, а `pull` не прошёл** — продолжать с локальной
  версией и предупредить, что она может быть не актуальна.
- **Если базы ещё нет, а `clone` не прошёл** — без базы навык соберёт только
  каркас без терминологии продукта; прямо сказать это пользователю, а не
  делать вид, что контекст загружен.

1. **Контекст и скоуп** — что за фича, зачем, границы. Обычно в документах
   проекта. Прочитать целиком.
2. **Макеты** — источник истины по UI. Принимаются двумя способами (см.
   «Приём макетов»). Без макетов UI-часть не финализируется — собирается
   каркас, недостающее уходит в вопросы автору.
3. **Матрица ролей** — кто что видит и может. Если нет — спросить.
4. **Смежные закрытые тикеты** (экспортом в `docs/`, не ссылкой на трекер) —
   язык и логику существующих механик нельзя ломать. Свериться.
5. **Зависимости и со-релиз** — связанные тикеты, которые релизятся вместе или
   поставляют часть механики (например, страница настроек из соседнего тикета).
   Зафиксировать в ТЗ, что обязано выехать одновременно и от чего зависит.

Если в проекте есть `CLAUDE.md` или аналог — прочитать его и применить
оттуда: терминологию (включая стоп-слова), формат вывода, роли, ограничения.

Раздел **«База знаний»** в проектном `CLAUDE.md` задаёт **путь к папке базы**
(см. Шаг 0), а не список файлов. Развернув базу, прочитать её собственный
корневой `CLAUDE.md` — он маршрутизирует, какие термины, стоп-слова и
`reference_*.md` брать по теме ТЗ. Файлы базы знаний имеют приоритет над любыми
предположениями навыка о конкретном продукте.

## Приём макетов

Макет — источник истины по UI. Поддерживаются два способа подачи, можно
смешивать:

**Способ A — скриншот с комментариями прямо в чате (основной, быстрый).**
Автор прикладывает картинку и пишет рядом, что на экране происходит. Агент
**сам вычитывает с картинки** то, что на ней видно: заголовки, надписи кнопок,
поля, плейсхолдеры, видимые состояния, расположение блоков. Спрашивает только
то, чего на картинке нет: поведение по клику, переходы, тексты скрытых модалок,
права, лимиты, пустые/ошибочные состояния, судьбу данных. Не выдумывать
надписи, которых на картинке не видно — уточнить.

**Способ B — файл-пояснение рядом с картинкой (под финал).** Картинка
`step1_rule_create.png` → пояснение `step1_rule_create.md` по шаблону
`mockup-explanation-template.md`. Имя файла — якорь связи «текст ↔ картинка»,
не сваливать несколько макетов в один файл. Используется, когда нужно
зафиксировать всё письменно и не зависеть от живого диалога.

**Грамматика комментариев к макету.** Чтобы агент не гадал, что значит подпись
автора, в комментариях (в чате или на врезке к картинке) используются метки:

- `[действие]` — что делает пользователь («[действие] клик по «Создать»→ открывается форма»)
- `[состояние]` — состояние элемента («[состояние] кнопка disabled, пока пусто поле «Промпт»»)
- `[текст]` — дословный UI-текст, который надо взять как есть («[текст] «Лимит исчерпан»»)
- `[роль]` — кому экран/элемент доступен («[роль] только Супер-админ»)
- `[edge]` — граничный случай, который автор уже знает («[edge] при 0 сообщений в выборке»)
- `[?]` — открытый вопрос самого автора, на который ответа пока нет

Метки необязательны; если их нет — агент извлекает смысл сам и уточняет
неоднозначное вопросом.

## Фича «по аналогии с существующей»

Частый и валидный приём: «сделать как у X, но для Y». Но «по аналогии»
молча предполагает, что читатель знает реализацию X — а агент её достроит
вымыслом. Поэтому:

- Описание эталонной механики (X) обязано **лежать файлом во входах** —
  экспорт тикета или ТЗ в `docs/`, а не только ссылка на трекер (агент не
  откроет внутренний трекер за авторизацией). Нет файла — нет аналогии;
  описывать с нуля или уточнить у автора.
- **Точки отличия перечисляются явно.** «Как у X» не освобождает от списка:
  где Y ведёт себя иначе, чего у X нет, что у Y есть сверх X. Именно отличия —
  основное содержание такого ТЗ, а не сама отсылка.

## Две формы ТЗ

ТЗ принимает одну из двух форм — выбрать по характеру задачи:

- **Форма A — новый объект/фича.** Вводится новая сущность, экран, механика.
  Используется порядок разделов ниже; пустые разделы не включаются.
- **Форма B — сквозное изменение поведения во многих существующих местах
  продукта** (переименование показателя, новая опция, влияющая на
  отчёты/экспорты/виджеты, и т. п.). Документ организован **не** по 12 разделам,
  а как **исчерпывающий перечень затронутых мест**: каждый отчёт, экран,
  фильтр, экспорт, виджет, дашборд, тултип — отдельным пронумерованным пунктом,
  для каждого «было → стало». Это house-форма для таких задач (демо-эталон —
  `examples/ТЗ_demo_переименование-показателя.formB.example.md`; полный боевой
  образец — внутренний тикет BA-7479, только локально у автора).

  Каркас формы B:
  1. **Что делаем** — суть в 2–4 абзаца; если вводятся новые величины — их
     определения здесь.
  2. **Зависимости и со-релиз** — связанные тикеты, что обязано выехать вместе.
  3. **Перечень затронутых мест** — по пункту на каждый экран/отчёт/экспорт;
     внутри пункта — ветки по режиму/настройке (см. «Вариативность») и
     дословные UI-тексты.
  4. **Затронуто, но НЕ меняется** — явный список смежных экранов/отчётов,
     которые остаются как есть (см. одноимённый раздел).
  5. Сквозные разделы как в форме A: права, миграция данных, онбординг,
     аналитика, критерии приёмки, таблица UI-текстов, открытые вопросы.

  Принцип полноты формы B: **перечислить КАЖДЫЙ экран/отчёт/экспорт/виджет,
  где встречается затрагиваемый элемент** (пройтись по продукту: отчёты,
  ленты, карточки, тултипы, сортировки, фильтры, экспорты, подписки,
  дашборды, виджеты). Пропущенное место = баг после релиза.

## Структура ТЗ нового объекта/фичи (форма A)

ТЗ организовано **двухуровнево по нумерации**:

- **С номерами — только пункты «Что нужно сделать»** и соответствующие им
  разделы тела (один к одному). Каждый номер = задача к выполнению, которую
  инженер может вычеркнуть.
- **Без номеров — общие и сквозные разделы**: вводная часть (Условия запуска,
  Состав/спецификация, Граничные случаи), Поведение при пересчёте, Поведение
  для существующих объектов, Права, Аналитика, Таблица UI-текстов, Открытые
  вопросы. Это **правила**, а не задачи; их нельзя «вычеркнуть».

Это решает две вечные боли документа: (а) перенумерация при добавлении/удалении
разделов больше не ломает внутренние ссылки — нумерованных разделов мало и они
привязаны к задачам; (б) с первого взгляда видно, что задача (число), а что
правило (заголовок без числа). **Сквозная единая нумерация по всем разделам
больше не используется.**

Раздел включается в документ, **только если в нём есть содержание**. Нечего
делать / не редактируется и не удаляется / не инструментируется / нет общих
UI-элементов / нет открытых вопросов → раздел **не вставлять вовсе**, не
писать «неприменимо», «нет», «не предусмотрено». Пропуск раздела — осознанное
решение, сверенное по чек-листу, а не забывчивость.

Разделы **«Сценарии» и «Критерии приёмки» — необязательные по умолчанию.** На
старте ТЗ (в блокирующих вопросах, до черновика) **спросить у автора**, нужны ли
они в этом документе. Это не «пустой блок», а сознательный выбор объёма ТЗ —
решает автор, не агент.

(Это правило — про разделы ТЗ верхнего уровня. Внутри UI-блока перечисление
состояний по-прежнему помечает неприменимые как «неприменимо» — это доказывает,
что состояние рассмотрено, см. «Как описывать UI-блок».)

### Порядок в документе

**Шапка (без номеров):**

- **Проблема** — что сейчас не так, какую боль испытывает пользователь, почему
  за это берёмся. Конкретная проблема, которую закрывает фича. Это house-
  дефолт первого блока, **НЕ «Контекст и цель»**. Если проект в своём
  `CLAUDE.md` задаёт иное название — следовать ему.
- **Решение** — как решаем на верхнем уровне, прозой: что меняется для
  пользователя и почему это закрывает проблему. Без пошагового списка действий —
  он идёт в «Что нужно сделать», здесь не дублировать.

**Список задач (внутри — единственная сквозная нумерация ТЗ):**

- **Что нужно сделать** — заголовок без номера, но **внутри нумерованный
  список** «1. Добавить…», «2. Убрать…», «3. Изменить…». Это раздел «что
  построить», НЕ описание рантайм-поведения (поведение — в сценариях и
  UI-блоках, настоящим временем). Один пункт — одно атомарное изменение, ИЛИ
  одна задача, которую логично решать единым подходом (например, добавить блок
  в три канала доставки — это **один** пункт с подпунктами 1.1, 1.2, а не три).
  **Каждый пункт = дословный заголовок соответствующего раздела тела** (одна
  формулировка, тот же порядок, та же нумерация). Не перефразировать в теле
  «аналитическими» заголовками («Оповещения в MAX и Telegram» вместо «Добавить
  блок анализа всплеска в текст оповещений в MAX и Telegram»). Правило для
  любых задач, не только объёмных. Подробно про группировку — см. «Группировка
  задач в один пункт с подпунктами»; про объём — см. «Объёмные задачи: обзор +
  подробное тело».

**Вводная часть (без номеров, до разделов тела):**

- **Условия запуска / шлюз применения** — если фича включается условно. См.
  отдельный раздел.
- **Состав / спецификация выводимого блока** — если одна и та же сущность
  показывается в нескольких каналах/экранах: единый источник истины для всех
  каналов. См. «Вводная часть ТЗ: общее до детального».
- **Граничные случаи** — общие для всех каналов: 0 значений, разные языки,
  превышение лимита и т. п. См. «Граничные случаи — стандартные семьи».

**Разделы тела (с номерами 1, 2, 3, …, по одному на каждую задачу из «Что
нужно сделать»):**

- **1. <дословный заголовок пункта 1>** — расположение, состояния, действия,
  «было/стало», крайние случаи. Подпункты 1.1, 1.2 — если в одной задаче
  несколько подпотоков (TG/MAX в одном, email в другом).
- **2. <дословный заголовок пункта 2>** — то же.
- и т. д.

Сквозные правила, относящиеся к нескольким разделам тела (Поведение при
пересчёте, Поведение для существующих объектов), могут вставляться **между**
разделами тела без номера — там, где это логически уместно.

**Хвост (без номеров):**

- **Поведение при редактировании и удалении** — про действия пользователя над
  самим объектом фичи (если фича вводит редактируемый объект). См. отдельный
  раздел.
- **Поведение сохранённого результата при изменении источников** — про
  ретроактивные изменения внешних данных. См. отдельный раздел.
- **Поведение для уже существующих объектов пользователя** — про
  ретроактивное применение фичи. См. отдельный раздел.
- **Права доступа** — только если фича вводит новую видимость/право (см.
  «Права доступа»). Пустой раздел НЕ включать.
- **Новые UI-элементы общего назначения** — если фича вводит элемент,
  затрагивающий весь продукт. Нет таких — раздел не включать.
- **Сценарии** *(необязательный — уточнить у автора)* — пользовательские
  потоки по шагам.
- **Критерии приёмки** *(необязательный — уточнить у автора)* — проверяемые
  условия «готово» в форме «Дано… когда… тогда…», а не пожелания. Сюда же —
  что считается дефектом.
- **Отображение в списках** — как объект выглядит в списках/отчётах.
- **Аналитика и события** — рассмотреть **две формы** независимо, обе
  уточнить у автора:
  - **(а) События для продуктовой аналитики.** Что инструментируем, в какой
    момент пишем событие, какие параметры. Сверять с метриками успеха из
    бизнес-контекста: заявленная метрика без события её не измерить.
  - **(б) Выгрузки для саппорта/продакта.** Нужен ли отчёт/выгрузка по фиче
    (CSV, экран в админке) — с какими полями, кому доступен, как запускается.
    Это другой жанр аналитики, не путать с продуктовыми событиями: аудитория
    иная, поля сырые, экран обычно админский. Молча не пропускать.

  Не инструментируется и не выгружается — раздел не включать. **Часто
  инструментация — отдельная задача в «Что нужно сделать»** и тогда становится
  пронумерованным разделом тела, а не сквозным хвостом. Решает автор.
- **Таблица UI-текстов под перевод** *(опциональный — уточнить у автора на
  старте)* — реестр всех интерфейсных текстов фичи (см. ниже). Для маленьких
  фич с предсказуемыми статичными текстами без склонений она часто избыточна,
  а для крупных и многоязычных — обязательна. Решение принимает автор; молча
  включать или молча опускать нельзя.
- **Открытые вопросы** — только то, что осталось нерешённым после диалога
  (ждёт инженера, отложено). Нет нерешённого — раздел не включать (не писать
  «открытых вопросов нет»).

**Лог решений в финальный ТЗ не выносится** — см. «Решения — в диалоге, не в
документе».

## Группировка задач в один пункт с подпунктами

Не плодить пункты в «Что нужно сделать», если они отвечают на одно «что»
разными «где». **Группировать каналы/экраны, которые решают одну задачу
одинаково, в один пункт с подпунктами.** Telegram + MAX + email — это
«добавить блок в текст оповещения» (одна задача, три канала с разной
вёрсткой): **один пункт** с 1.1 (TG/MAX) и 1.2 (email), а не три отдельных
пункта.

Отдельные пункты — для **разных задач**: push в моб. приложении и
разворачиваемый аккордеон в веб-интерфейсе — это разные задачи, у них разная
UI-механика. Тут группировать нельзя.

**Сигнал «надо группировать»:** формулировки пунктов начинаются одинаково и
отличаются только каналом или экраном.

**Сигнал «не группировать»:** даже если каналы те же, механика разная
(переход против раскрытия; статичный текст против интерактивного элемента;
push-баннер против экрана внутри приложения).

## Заголовок тикета — разграничивающая характеристика

Заголовок ТЗ/тикета должен включать **то, что отличает фичу от похожих в
архиве проекта**. Не «Добавить анализ всплесков в оповещениях», а
«Добавить анализ всплесков **в оповещения по условию "Количество сообщений
увеличилось…"**». Если в продукте есть несколько типов сущностей и фича
касается только одного — тип в заголовке.

**Сверка:** можно ли по одному заголовку понять, какой именно скоуп? Если
нет — заголовок недостаточно специфичен; уточнить у автора.

## Дословное перечисление типов сущностей под общим правилом

Если правило применяется к **классу объектов**, перечислить **дословно** все
элементы класса в самой формулировке, а не «применяется к оповещениям типа
"увеличилось"» в общем виде. За такой формулировкой обычно стоит конечный
список из нескольких типов — обобщение скрывает половину скоупа.

**Сигналы «надо разворачивать»** в формулировке:
- «оповещения типа …»
- «события вида …»
- «отчёты с условием …»
- «все правила с настройкой …»

Найдя такой оборот, спросить автора: какие именно типы, дать полный список.
Дальше — перечислить дословно (буллетами) в тексте ТЗ, в том самом месте,
где правило применяется.

## Не тянуть в продуктовое ТЗ технические характеристики, не влияющие на UX

Характеристики внешнего сервиса/API (длина ответа ML, формат внутренних
чисел, таймауты сервиса, точность округления, кодировка) **в продуктовое ТЗ
не выносить**, если они не приводят к видимому пользователю поведению.

**Граница:**
- Влияет на UX → в ТЗ. Пример: «формулировка обрезается с „…“ после 500
  знаков» — это **поведение, которое видит пользователь**.
- Не влияет → в API-тикет, не в ТЗ. Пример: «ML возвращает не больше 500
  знаков» как технический контракт — пользователю этой границы не видно,
  значит в ТЗ это шум.

Если сомневаетесь — спросите себя: «если эту строку убрать, изменится ли
что-то в том, что увидит пользователь?». Нет — убрать.

## Вводная часть ТЗ: общее до детального

Если **одна и та же сущность отображается в нескольких каналах/экранах** (один
блок в Telegram + email + интерфейс + моб. приложение; один показатель в
нескольких отчётах; одно правило, влияющее на разные сценарии), собрать всё
общее в **вводную часть** между «Что нужно сделать» и детальными разделами по
каждому каналу/экрану. В вводную часть идут разделы, которые иначе пришлось
бы повторять (или, что хуже, расходиться) в каждом канале:

- **Условия запуска / шлюз применения** — когда фича включается, когда нет.
- **Состав / спецификация выводимого блока** — поля, форматы, правила
  склейки, что вырезается при отсутствии значения.
- **Граничные случаи** — общие для всех каналов: 0 значений, разные языки,
  превышение лимита и т. п.

Только после вводной части идут разделы по каждому каналу/экрану — в них
**только специфика этого канала** (расположение, «было/стало», особенности
рендеринга), без повторения общих правил. Один источник истины — меньше
рассинхрона между каналами.

Если фича работает **в одном месте**, такого деления не нужно — общие правила
ложатся inline в этот раздел. Не плодить «вводную часть» искусственно.

## Условия запуска / шлюз применения

Если фича **включается условно** (по типу события, объёму данных, наличию
внешнего результата, тарифу — что угодно, что отсекает часть случаев), вынести
условия запуска **отдельным разделом сразу после «Что нужно сделать»**, до
описания каждого канала/экрана.

- Это шлюз ко всем каналам и экранам сразу — читатель должен увидеть его до
  деталей по каждому из них, а не выкапывать в конце.
- Все условия — нумерованным списком с пометкой «выполняются *все*» или «*хотя
  бы одно*»; не оставлять формулировку неоднозначной.
- В каждом разделе тела достаточно ссылаться «если условия не выполнены —
  канал/экран работает в прежнем формате», не повторяя список условий.

## Делегирование части скоупа в связанный тикет

Если часть фичи (отдельный канал, отдельная платформа, отдельный экран)
**существенно отличается по реализации** и требует своего тикета — не
дублировать описание в обоих ТЗ. В основном ТЗ:

- одна-две строки, что туда передаётся и за что отвечает основной ТЗ
  (например: «передаём то же содержание оповещения с анализом всплеска, что и
  в других каналах»);
- **прямая ссылка** на связанный тикет с полным описанием. В Jira — добавить
  связь `relates to` и в теле дать гиперссылку на тикет.

Не делегировать молча: явно написать, что детальное описание находится там,
и сверить с автором, что связанный тикет реально существует и описывает то,
что нужно. Ссылка «см. п. 3 в другом ТЗ» без рабочего URL — не делегирование,
а потеря информации.

## Поведение сохранённого результата при изменении источников

Отдельный паттерн, который **не путать** с «редактированием/удалением объекта
фичи». Описывает, что происходит с уже выпущенным/сохранённым результатом,
если позже изменились внешние данные: настройки темы, переименование
показателя, перерасчёт. Типовые решения:

- Сохранённый результат — исторический срез: не пересчитывается, остаётся как
  был на момент выпуска. Это часто верное решение для оповещений, отчётов,
  снимков.
- Сохранённый результат пересчитывается на лету при каждом обращении. Это
  редкое решение, требующее явного запроса от автора.

Ставить ближе к концу документа (отдельным коротким разделом перед
«Граничными случаями» или внутри них), а не сразу после «Что нужно сделать».

## Объёмные задачи: обзор + подробное тело

Для большой задачи (несколько направлений, много экранов) «Что нужно сделать»
работает как **оглавление**, а детали выносятся в тело документа двумя уровнями:

- **Вверху — «Что нужно сделать»: краткий обзор.** Каждый пункт = директивный
  заголовок («1. Изменить клиентский путь создания Правил…») + 1–5 коротких
  подпунктов, что входит в этот блок. Без макетов и без дословных UI-текстов —
  только суть. Это карта задачи на один экран, чтобы читатель сразу увидел
  объём.
- **Ниже — тело: по разделу на каждый пункт обзора**, с той же нумерацией и
  заголовком (пункт 1 ↔ раздел 1, пункт 5 ↔ раздел 5 — один к одному). Внутри
  раздела — подсекции по экранам/блокам (1.1, 1.2, …), и **каждый макет
  описан**: скриншот + расположение → состояния → действия → дословные тексты
  (порядок — см. «Как описывать UI-блок»). Скриншот без описания не считается
  раскрытием.
- **Соответствие держать строгим:** сколько пунктов в обзоре — столько разделов
  в теле, в том же порядке, с теми же формулировками заголовков. Пункт обзора
  без раздела в теле или раздел в теле без пункта в обзоре — рассинхрон, ловить
  на самопроверке.
- **Сквозные блоки — отдельными разделами** (онбординг, уведомления о
  лимитах, права): если они общие для нескольких пунктов, не дублировать в
  каждом, а вынести и сослаться («онбординг новых правил описан в разделе
  "Онбординг"»).

Для **небольшой задачи** раскрытие не нужно: «Что нужно сделать» остаётся плоским
списком, тело его не дублирует. Не раздувать маленькое ТЗ двухуровневой
структурой ради формы.

## Решения — в диалоге, не в документе

Концептуальные развилки, пройденные при проработке (что решили и почему, что
отклонили), **не вписываются в финальный ТЗ.** Их место — диалог с продактом:
проговорить выбор и его причину в чате, дать автору принять решение. В документ
идёт только результат (готовое требование), а не история, как к нему пришли.

- Раздел «Лог решений» в ТЗ не создавать.
- Рационал неочевидного требования, если он нужен прямо в тексте, давать
  короткой скобкой рядом с пунктом (см. «Тон» — причина в скобках), а не
  отдельным разделом-историей.
- Если автор просит зафиксировать историю решений — отдать её отдельным
  сообщением в чат или отдельным файлом-заметкой, но не в теле ТЗ.

## Работа с открытыми вопросами (гибрид)

Всё, что не разрешилось по входам, **не достраивается молча**. Три уровня:

- **Блокирующий вопрос** (меняет структуру ТЗ) — задать сразу, до черновика.
- **Маркер незакрытого** — в черновике на месте дыры ставить видимую врезку,
  чтобы автор физически видел пробел. В Jira wiki markup:
  `{panel:title=❓ ТРЕБУЕТ РЕШЕНИЯ|borderColor=#CC0000}…что именно неясно…{panel}`.
  В markdown — блок `> ❓ **ТРЕБУЕТ РЕШЕНИЯ:** …`.
- **Батч уточнений** — накопленные неблокирующие вопросы задать автору одним
  блоком (по возможности через структурированный выбор вариантов), ответы
  вплести в разделы и снять соответствующие маркеры.

К финалу маркеров `❓` в документе быть не должно: каждый либо закрыт ответом,
либо перенесён в раздел «Открытые вопросы» с явной пометкой статуса. В
headless-прогоне без собеседника вопросы не теряются — возвращаются списком в
конце, а ТЗ помечается незавершённым до их закрытия.

## Как описывать UI-блок

Строгий порядок для каждого элемента:

**расположение** (где живёт, как сюда попадают) → **состояние по умолчанию**
(что видно до действий, что предзаполнено) → **все состояния** → **действие
пользователя** (что можно сделать, что происходит после) → **крайние случаи**.

«Все состояния» — перечислить каждое, неприменимое помечать «неприменимо», не
пропускать: активно / неактивно (disabled) / недоступно (скрыто по правам) /
загрузка / ошибка / пустое состояние.

UI-тексты — **дословно**. Динамические — шаблоном с `[переменная]` и правилом
подстановки (включая склонения) рядом.

## Вариативность по режиму/настройке

Если поведение зависит от настройки, режима или роли — **специфицировать каждую
ветку отдельно**, а не одним размытым «в зависимости от выбора». Для каждого
значения настройки: что показываем, какие тексты, какие тултипы, как считается
число. Обязательно добавить ветку **«вне зависимости от выбора»** — то, что
одинаково во всех режимах (часто туда уходят переименования и общие тултипы).
Эталон — BA-7479: каждый экран расписан как «если индекс A / если индекс B /
вне зависимости».

## Затронуто, но не меняется

Для сквозного изменения явно перечислить смежные экраны/отчёты, которые
**остаются без изменений**, и написать это словами («в отчёте "Авторы" колонка
"Аудитория" — без изменений»). Это не формальность: без явного «не трогаем»
разработчик либо «починит» неизменное место под общий паттерн, либо забудет
проверить, что не сломал его. Граница «что НЕ входит» на уровне конкретных
экранов — такая же часть ТЗ, как и сами изменения.

## Расчётные величины и формулы

Если фича вводит или меняет отображаемое число (индекс, метрику, агрегат):

- **Определить формулу один раз**, в явном виде, со всеми входами
  (`Аудитория = Аудитория соцмедиа + Аудитория онлайн-СМИ`), и расшифровать
  каждый член.
- Указать **единицы, округление и правила уникализации/дедупликации**
  («с уникализацией по месту публикации», «без уникализации») — именно здесь
  расходятся ожидания и всплывают баги.
- **Ссылаться на это определение по якорю** из всех мест, где число выводится
  («считается по формуле из п. X»), а не переписывать формулу заново в каждом
  разделе. Одно определение — один источник истины, меньше рассинхрона.

## Поведение для уже существующих объектов пользователя

**Любая фича, которая меняет или добавляет поведение к классу уже
существующих пользовательских объектов** (оповещений, фильтров, правил,
подписок, дашбордов, промптов, экспортов), обязана содержать **отдельную
явную строку** о ретроактивном применении:

> «У уже созданных на момент релиза [объектов] — [как себя ведут], у вновь
> создаваемых — [как]».

Без этой строки непонятно, нужна ли миграция, и непонятно, что увидит
существующий пользователь сразу после релиза. Это **шире, чем переименование
примитива** — даже добавление новой опциональной функциональности (как блок
анализа в существующих оповещениях) требует решения «применять ли к уже
созданным».

**Два частых случая:**

- **Переименование/замена общей сущности.** Переименовывается или заменяется
  примитив, который пользователи уже встроили в свои объекты (фильтр, тег,
  сортировка, поле). Описать судьбу **каждого типа** пользовательских
  объектов, где сущность могла быть сохранена: персональных фильтров, правил,
  промптов, подписок, шаблонов дашбордов, экспортов. Пример из BA-7479: «у
  пользователей с ранее созданными фильтрами/правилами с фильтром "Аудитория"
  после релиза он заменяется на "Аудитория соцмедиа"». Не указать это —
  пользовательские объекты осиротеют или сломаются.
- **Добавление функциональности к существующим объектам.** Фича расширяет
  поведение (новый блок в уведомлении, новое поле в карточке, новая опция в
  настройках). Решить: применяется ли к уже созданным или только к новым.
  Дефолт обычно «применяется ко всем», но решение должно быть **записано
  явно** — иначе разработчик угадает, и угадает не туда.

Перечислить все типы объектов, где сущность затронута, и для каждого — что
с ней происходит после релиза.

## Тон и формулировки

- **Два регистра глагола, не смешивать в одном предложении.** Инфинитив-команда
  для того, что надо построить («добавить кнопку», «вынести пункт», «выводить
  блок») — это язык раздела «Что нужно сделать». Настоящее время для поведения
  системы в рантайме («открывается страница», «выводится плашка», «пользователь
  нажимает») — не будущее («откроется»), а настоящее, как будто уже работает, —
  это язык сценариев и UI-блоков.
- **Конкретные числа вместо «несколько».** Любой порог называть цифрой:
  «максимум 100 символов», «минимум 20 символов», «не более 5 одновременно».
  Никаких «немного», «достаточно», «несколько».
- **Причина неочевидного правила — в скобках рядом.** «По умолчанию доступно
  только админам (защита от незапланированного расхода ресурса)». Это защищает
  сознательное ограничение от того, чтобы разработчик «починил» его как баг.
- **Нейтральный, не-маркетинговый регистр.** Только поведение. Ноль «удобно»,
  «красиво», «интуитивно», «легко». ТЗ описывает, а не продаёт — это другой
  жанр, чем маркетинговые материалы.

## Внутренние перекрёстные ссылки

Ссылки «см. §N» / «см. п. N» внутри ТЗ **минимизировать**. Они ломаются при
каждой перенумерации (а она случается почти каждую правку), и читатель
получает битый якорь.

- **Предпочитать самодостаточные формулировки** — короткое повторение
  условия в месте использования («если условия запуска не выполнены —
  отправляется в прежнем формате»), а не ссылку «см. п. 3».
- **Если ссылка действительно нужна** (повторение реально утяжелит чтение —
  например, длинная формула расчёта), ссылаться **по названию раздела**,
  а не по номеру: «см. раздел "Условия запуска"», а не «см. п. 3».
- **Нотация в проекте — "п. N", не "§N".** Символ параграфа в текстах ТЗ не
  использовать. Это касается и текста, который агент пишет сам, и шаблонов
  в этом навыке.

При финальной проверке: пройти все «см. п. N» / «см. § N» и убедиться, что
номера актуальны после последней правки нумерации. Лучше — переписать на
название раздела.

## Права доступа

Формулировать через видимость и право, а не через роль абстрактно.
Не «недоступно роли X», а **«роль X без права Y не видит элемент Z в форме
W»**. Это убирает двусмысленность для разработки.

## Модалки

Каждую описывать полностью: заголовок + текст тела + все кнопки с их исходами +
поведение закрытия (×). Если у модалки несколько вариантов — каждый отдельно,
со своим условием появления.

## Уведомления

Каждое: канал (in-app / email / push) + роли-получатели + тема (для email) +
полный текст + ссылки (куда ведут).

## Онбординг новой фичи

Обязательный пункт для проверки — его регулярно забывают, и фича выходит
без объяснения для пользователя. Для **каждой новой или заметно изменённой**
точки (новый раздел, перенос пункта меню, новая механика, новая точка входа,
новое поле с неочевидным смыслом) проверить: нужен ли онбординг и подан ли он
на вход.

- **Если автор подал онбординг** (плашки/туры/подсказки/модалки/пустые
  состояния с объяснением) — описать его как UI:
  - **аудитория показа** — всем / только существующим пользователям / только
    созданным после релиза. Частый кейс из BA-7479: новым пользователям онбординг
    не показываем (для них поведение уже дефолтное).
  - **триггер** — первый заход / N-й раз / по условию (вход на конкретный экран).
  - последовательность шагов, дословные тексты, кнопки и исходы («Применить»,
    «Понятно», «Пропустить»).
  - **все пути прекращения показа** — их обычно несколько (закрыл/применил
    здесь; сделал то же действие в другом месте, например сохранил в Настройках).
    Перечислить каждый, иначе онбординг «залипнет» или исчезнет не вовремя.
  - **подтверждение после действия** — тост/плашка с текстом по ветке выбора
    («Выбран индекс …»).
- **Если онбординга на вход НЕ подано, а фича на него напрашивается** — НЕ
  выдумывать тексты и шаги. Подсветить маркером `❓ ТРЕБУЕТ РЕШЕНИЯ` в нужном
  месте ТЗ и уточнить у автора: нужен ли онбординг здесь, какой формат, какие
  тексты. Это решение продакта, а не домысел агента.
- **Если онбординг сознательно не нужен** — раздел про онбординг не добавлять
  (правило «пустой блок не включать»). Что его рассмотрели — фиксируется через
  чек-лист, а не пустым разделом «онбординг не предусмотрен».

Сигналы, что онбординг почти наверняка нужен (повод поднять вопрос): пункт меню
переехал на новое место; появился новый раздел; знакомое действие теперь
расходует платный ресурс; новая механика меняет привычный сценарий старожилов.

## Журнал / аудит-лог действий

Поверхность, которую регулярно забывают. Для фичи указать: **какие действия
пишутся в журнал** и **с каким текстом** (дословно, с шаблоном переменной, если
в тексте есть имя пользователя/объекта). Если фича ничего не журналирует —
раздел не включать (но проверить это по чек-листу, а не пропустить по
забывчивости).

## Асинхронный / длительный процесс

Если действие запускает обработку, которая идёт заметное время (обработка
массива, разметка, экспорт, импорт), описать весь жизненный цикл — недостаточно
состояний «активно/ошибка»:

- **Запуск** — что показываем в момент старта.
- **В процессе** — лоадер/прогресс-бар; что показывает прогресс (проценты,
  оставшееся время, счётчик); поведение в очереди до взятия в работу.
- **Уход со страницы во время процесса** — можно ли уйти; что с процессом;
  лочатся ли элементы управления.
- **Обновление страницы (refresh) во время процесса** — процесс продолжается;
  после refresh показываем текущий статус, а не пустой экран.
- **Завершение** — уведомление/смена состояния; прогресс-бар обязан
  завершиться синхронно с уведомлением о завершении.
- **Прерывание / отмена** — можно ли прервать; **что происходит со
  списанным ресурсом** (возврат/частичный возврат/невозврат — решение записать).
- **Ошибка от внешнего сервиса** — что показываем; списывается ли ресурс;
  как повторить.

## Граничные случаи — стандартные семьи

Проверить каждую семью применительно к фиче; неприменимое помечать
«неприменимо». Именно здесь ТЗ обычно дырявое и баги всплывают в QA:

- **0 результатов** — выборка/фильтр не дали ничего: что показываем, какой
  текст, не открываем ли зря окно подтверждения.
- **Фактических меньше запрошенных** — пользователь запросил N, доступно M<N.
  Поведение определить и для окна подтверждения/предпросмотра (показываем M,
  не N), и для самого выполнения (обрабатываем/списываем M). Текст «больше
  нет» — только когда остаток равен 0, не когда меньше запрошенного.
- **Исчерпание лимита/квоты/ресурса** — что показываем при нехватке; разный
  текст для разных ролей, если у них разные пути пополнения.
- **Параллельные запуски** — можно ли запустить процесс, пока идёт предыдущий;
  если нет — какой текст ошибки и при каком условии (например, лимит
  одновременных).
- **Максимальная длина ввода** — лимит символов в полях; что на (лимит+1)-м
  символе (блок ввода + текст ошибки дословно).
- **Обрыв сети посреди операции** — что с результатом и со списанным ресурсом;
  как восстановиться при возврате связи.
- **Отсутствующее значение динамического поля.** Для каждого выводимого поля
  (источник, тональность, имя, агрегат) — что показываем, если
  ML/расчёт/внешний сервис **не вернул значение**: скрываем строку целиком,
  показываем «—», явный плейсхолдер, или иначе. Не подразумевать «значение
  всегда есть» — решение фиксируется явно.
- **Не русский / неподдерживаемый язык контента.** Для продуктов, работающих
  с многоязычным контентом (мониторинг СМИ, чаты, отзывы), проверить: что
  происходит, если входящий контент не на ожидаемом языке. Анализ всё равно
  проводится? На каком языке выводится результат? Есть ли отдельная ветка
  «контент не на поддерживаемом языке»? Не оставлять подразумеваемым.

## Таблица UI-текстов под перевод

**Опциональный раздел — на старте уточнить у автора, нужна ли она.** Для
маленьких фич с очевидными статичными текстами без склонений таблица обычно
избыточна; для крупных и многоязычных — обязательна. Решение принимает автор.

Если автор подтвердил, что таблица нужна, — собрать ВСЕ интерфейсные тексты
фичи в одну таблицу. Сами переводы здесь не делать — это реестр под перевод,
перевод собирается отдельно. Колонки:

| id | Текст-исходник | Где встречается (экран / элемент) | Тип (статичный / динамический) | Примечание (переменные, склонения, лимиты длины) |

Каждый текст из разделов выше (заголовки, кнопки, подписи, плейсхолдеры, тексты
модалок, уведомлений, ошибок) должен попасть в таблицу. Динамические — с
шаблоном переменной и правилом подстановки в примечании.

## API — отдельно

Требования к API выносить в **отдельный тикет**, не смешивать с продуктовым ТЗ.
В ТЗ — поведение продукта, не контракт интеграции.

## Выход — файл

Результат сохранять **файлом**, а не только печатать в чат — продакту нужен
готовый артефакт для вставки в трекер.

- Имя: `ТЗ_[тикет]_[краткое-имя].md` (например `ТЗ_BA-7581_smartboost-rules.md`).
  Если номера тикета нет — спросить или взять краткое имя фичи.
- Содержимое — в разметке целевого трекера (см. «Формат вывода»).
- Перед сохранением прогнать самопроверку по чек-листу и проверить, что в файле
  нет оставшихся маркеров `❓`.

## Формат вывода

Markdown по умолчанию. **Если контекст проекта задаёт другой формат**
(Jira wiki markup, Confluence, Notion-разметка) — следовать ему и не
использовать синтаксис, который в целевой системе не отрендерится.

⚠️ **Jira Server/DC ≠ Jira Cloud.** Server/Data Center понимает классический
wiki markup (`h1.`, `||шапка||`, `{panel}`, `{code}`). Jira Cloud в описании
задач wiki markup НЕ рендерит — там markdown/ADF. Перед выводом свериться, что
формат из `CLAUDE.md` соответствует реальному трекеру; при сомнении — уточнить.

## Чек-лист перед сдачей

- [ ] Заголовок тикета включает разграничивающую характеристику — по нему можно понять конкретный скоуп фичи (не «Сделать X», а «Сделать X для условия Y»)
- [ ] Первый блок — «Проблема» и «Решение» (house-дефолт, НЕ «Контекст и цель»); «Решение» верхнеуровневое, не дублирует «Что нужно сделать»
- [ ] **Нумерация в ТЗ — только для пунктов «Что нужно сделать»** и соответствующих им разделов тела (1, 2, 3, …); вспомогательные/сквозные разделы (Условия запуска, Состав блока, Граничные случаи, Поведение при пересчёте, Поведение для существующих объектов, Права, Аналитика, Таблица UI-текстов, Открытые вопросы) идут БЕЗ номеров
- [ ] «Что нужно сделать» написан директивными инфинитивами; **группировка по принципу «одна задача, разные каналы» применена** (TG/MAX/email в одном пункте с подпунктами 1.1, 1.2, а не три отдельных пункта)
- [ ] **Каждый пункт «Что нужно сделать» становится дословным заголовком раздела тела** (та же формулировка, тот же порядок, та же нумерация); в теле нет «аналитических» переименований
- [ ] Если правило применяется к классу объектов («оповещения типа …», «события вида …», «отчёты с условием …»), все элементы класса **перечислены дословно** в самой формулировке
- [ ] Для условно-включаемой фичи введён раздел «Условия запуска» во вводной части (без номера), до пронумерованных разделов тела
- [ ] Если одна и та же сущность выводится в нескольких каналах/экранах — общее (Условия запуска, Состав/спецификация, Граничные случаи) собрано во **вводной части** (без номеров), до пронумерованных разделов тела; в разделах по каналам нет повторения общих правил
- [ ] Если фича меняет/добавляет поведение к классу существующих объектов пользователя — есть **явная строка** «у уже созданных на момент релиза [объектов] — …, у вновь создаваемых — …»
- [ ] Технических характеристик сервиса/API, не влияющих на видимое пользователю поведение (длина ответа ML, формат внутренних чисел, таймауты сервиса), в продуктовом ТЗ нет — они в API-тикете
- [ ] Часть скоупа, делегированная в связанный тикет, обозначена 1–2 строками + прямой ссылкой; описание не дублируется
- [ ] Терминология: используется «канал / экран / место отображения», а НЕ «поверхность»; внутренние ссылки — «п. N» (а НЕ «§N»), и по возможности заменены на ссылку по названию раздела
